# RELAY_DESIGN — リレー方式の設計案

方式は「重複排除つきのフラッディング(受信したら再送)」から始める。単純で、中継役を決めなくてよい。
混雑時の共倒れを避ける工夫を入れ、S4 で効果を測る。

## 1. 受信時の処理

1. 署名(MIC)を検証。不正なら破棄(カウンタに記録)
2. `(src, seq, type)` が既知なら破棄
3. 既知にして、ローカルで処理(表示、ACK 判定、ログ)
4. ttl > 0 なら再送を予約(後述)。ttl は 1 減らす

## 2. 再送の予約

- **ランダムな待ち時間(バックオフ)** を置く。範囲は、フレームの送信時間の数倍(初期案:SF7 で 50〜300ms)。
- **優先度:** SOS < INSTRUCT < ACK < REPORT < BEACON の順に待ち時間を短くする(SOS が最優先)。
- **再送の抑制:** 待っている間に、同じフレームの再送を他のノードから `k` 回(初期案 k=2)聞いたら、自分の再送を取りやめる。
- **送信前のキャリアセンス:** 他の電波が出ていれば待つ。値と手順は規格で確認(COMPLIANCE.md)。
- **送信時間の予算管理:** 1時間あたりの送信時間を集計し、上限に近づいたら、優先度の低いフレーム(BEACON、REPORT)から送らない。上限値は COMPLIANCE.md で確認した値を使う。

## 3. 送信元の再送(ACK がないとき)

- REPORT / SOS は、ACK(近傍またはサーバー)を待つ。
- なければ、待ち時間を延ばしながら再送する(初期案:5秒 → 10秒 → 20秒、最大 N 回)。
- 再送のたびに seq は変えず、同じ `(src, seq)` を使う(重複排除と ACK の突き合わせのため)。
- 最大回数に達したら「未達」を表示し、止める(ずっと送り続けない。送信時間の予算を守るため)。

## 4. 出口(GATEWAY)の処理

- LoRa で受信した REPORT / SOS を MQTT で PC に出し、成功したら「サーバー到達」の ACK を LoRa で送る(ack_kind=2)。
- MQTT が切れているときは、受信したフレームをキューに溜める(上限あり)。回復したら送る。
- PC から来た指示(MQTT)を、INSTRUCT フレームにして LoRa で放送する。

## 5. 実験で振るパラメータ

| パラメータ | 候補 |
|---|---|
| SF | 7 / 8 / 9(10以上は送信時間が長く、規制の確認が済むまで使わない) |
| BW | 125kHz |
| 符号化率 | 4/5 |
| 送信出力 | 10dBm から開始。**12dBm を超えない** |
| ttl | 2 / 3 / 4 |
| バックオフ範囲 | 50〜300ms、100〜600ms |
| 抑制の閾値 k | 1 / 2 / 3 |

## 6. 測るもの(S4)

- 到達率(送信した数に対して、各ノードが受信できた割合)
- ホップ数(受信時の ttl の減り方)
- 遅延(送信から受信までの時間)
- 重複して再送された回数(混雑の指標)
- 送信時間の合計(予算に対する使用率)

## 7. 既知の弱点(記録しておく)

- 全員が再送する方式は、台数が増えると混雑で共倒れになりやすい。p-02 は3台なので、この弱点は小さく見える。**台数を増やしたときの挙動は、別途シミュレーションか追加の実験が必要**と記録する。
- 孤立したノードには届かない。
- 中継役は常に受信を待つので、電池を消費する(S8 で測る)。
