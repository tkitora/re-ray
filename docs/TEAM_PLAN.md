## 1. 今期つくるもの(10/20 に決めたこと)

| 項目 | 決定 | 影響するパート |
|---|---|---|
| 平時の文字起こし(話した内容がグラスに出る) | **今期に入れる。** 音声→文字はスマホ/PC のアプリで行い、文字をサーバーの `POST /api/messages` に送る。端末側(マイコン)には音声処理を入れない | Web/サーバー(アプリの置き場所は要決定)、ハード(表示) |

| 位置(ポジション) | **番号付きポジション(1〜N)を動的に決める。** 名前と場所は本部の画面で変えられる(サーバーの表)。LoRa には番号だけを載せ、指示コードのパラメータと定型信号の「今いる場所」に使う | 共通仕様、サーバー、Web、ハード |
| 定型信号の数 | 4 つに限らず、必要なぶんを表に持つ(上限 31。LoRa の都合) | 共通仕様 |
| LoRa の実機作業 | **T-Beam 未着のため後回し。** 先に Wi-Fi 経路で全部つなぐ | ハード |

### 1.1 共通仕様に足すもの(横断役へ依頼)

| 表 | 置き場所 | 中身 |
|---|---|---|
| 定型信号コード(現場 → 本部) | 共通仕様 01 | 既存の 1〜4 に加えて必要なぶん。各コードに「グラスに出す文」。**ポジション番号を添えられる** |
| 指示コード(本部 → 現場)【新規】 | 共通仕様 01 | 例: 1=待機、2=移動、3=集合、4=撤収、5=物資搬送、6=流入停止、7=退避。各コードに「パラメータの意味」(多くはポジション番号)と「グラスに出す文」 |
| ポジション表 | サーバーの表(DB)。共通仕様には「番号は 1〜N、0 は未指定」の決まりだけ | 番号、名前、場所の説明。Web から編集。端末は Wi-Fi 接続時に受け取る |
| MQTT の `instruct`(下り)【新規】 | 共通仕様 02・03 | `{"v":1,"type":"instruct","src":"pc","dst":"all","seq":8,"mid":13,"ts":...,"code":2,"param":3}`。トピック `reray/v1/down/{id}/instruct`、`reray/v1/down/all/instruct`。出口が LoRa の INSTRUCT に直す |
| `signal` に `pos`【追加】 | 共通仕様 02 | 定型信号に今いるポジション番号(任意、0 なら未指定) |

## 3. 段階と目標

ハードの S0〜S8、サーバーの M0〜M5 を、チームの 5 段階に束ねる。目標は「できたと判定できる基準」。

### 段階 0:仕様の凍結と規制の確認(10/20 〜 10 月末)

| 作業 | 担当 | 目標 |
|---|---|---|
| §1.1 の表を共通仕様に書き、既存の【案】を外す。修正案(10/16)の `mid`/`ack_mid`、online 判定、心拍、seq の始まりを決着 | 横断 + 各パート | 共通仕様に【案】が残っていない |
| 電波法: `COMPLIANCE.md` の確認欄 11 項目。**総合通信局か登録証明機関に「技適機器を自作ファームで使えるか」を問い合わせる** | ハード A | 回答が記録されている。NG なら段階 3 を代替案に切り替える |
| 文字起こしアプリの方式を決める(ブラウザの音声認識 API か、スマホの OS 機能か) | 文字起こし | 1 文を文字にして API に送る試作が動く |
| 授業の提出物(システム構成図)を 1 枚に | 横断 | プレゼン 10 枚目の図と、共通仕様の値が一致 |
| Web の 6 画面 + ポジション表の紙芝居 | Web | API 一覧(サーバー INTERFACES §4)と 1 対 1 で対応 |

### 段階 1:パート別に、実機なし・電波なしで動くところまで(11 月上旬)

| パート | 作業 | 目標 |
|---|---|---|
| サーバー | M1〜M4(疑似端末)+ ポジション表・指示の API | 疑似 100 件が欠け・重複なく保存。異常系が全部期待どおり |
| Web | モック API で W1〜W6、ポジション表の編集 | 画面から文字と指示を送り、「N 台中 M 台に届いた」とログが見える |
| 文字起こし | 音声 → 文字 → API | 話した 1 文が、サーバーのログに文字で残る |
| ハード B | S1: GUIDE01 に文字が出る、タッチが取れる | 日本語の 1 行の文字数・行数を実測。100 回更新で崩れない |
| ハード A | T-Beam 到着後の S2(**送信以外**): GPS、電池、ボタン、UART、Wi-Fi で MQTT | T-Beam が Wi-Fi 端末として `signal`/`status` を本物のサーバーに送れる |

全体目標: **電波を出さずに「ボタン → サーバー → 画面」「画面/文字起こし → サーバー → グラス」の 2 本が Wi-Fi で通る。** LoRa が最悪ダメでも、ここまでで発表のデモは成立する。

### 段階 2:結合 A(室内、LoRa なし)(11 月中旬)

全員で 1 日取る。

- 1 セット(T-Beam を Wi-Fi 端末として + XIAO + GUIDE01)と、サーバー + Web + 文字起こしをつなぐ
- 目標: **ボタンの定型信号(ポジション付き)が Web の一覧に出る。Web の指示と、文字起こしの文がグラスに出る。ログが残る。** 各 10 回
- 判定表の「一覧」「送信」「届いた確認」「ログ」「グラス表示」をここで仮判定

### 段階 3:LoRa(段階 0 の規制確認が OK で、T-Beam が揃ってから)(11 月下旬 〜 12 月上旬)

| 作業 | 目標 |
|---|---|
| S2 送受信、S3 ACK、S4 3 台リレー | 2 台で 10 回連続。A→B→C の到達率 90% 以上(試験配置) |
| S5 出口(= サーバー M5)。INSTRUCT の LoRa 送出 | 出口の Wi-Fi を切っても現場側が動き、復旧後に溜まった分が届く。指示が LoRa 経由でグラスに出る |
| S6 結合 B | グラスの表示が「送信済み → 近傍 → サーバー到達」と進む |

**規制確認が NG だった場合:** 実機の電波は出さない。リレーのロジックは PC 上の検証結果で示し、実機デモは Wi-Fi 経路のみ。「LoRa 部分は設計と机上検証まで」と正直に書く。

### 段階 4:実測と判定(12 月中旬)

- S7 屋外: 見通しで 100m 刻み・600m まで、市街地、人の多い場所。条件(高さ・持ち方・SF)を揃えて記録
- S8 電池: 受信待ちで何時間か
- 目標: **企画書の主張ごとに OK / NG / 一部 / 未確認を全部付ける。** 600m に届かなくても数字が出れば成果

### 段階 5:発表準備(発表日の 2 週間前から)

- デモ台本: プレゼン 5 枚目の「電波が止まった」を実機で再現する(出口の Wi-Fi を切る → 現場のボタン → LoRa 経由で Web に出る → 本部から指示 → グラスに出る)
- 判定表と実測の表を、プレゼンの「約 600m は想定値」の注記に差し替える
- 展望: SIM、モジュール

## 5. 進め方の決まり

- **週 1 回、結合の時間**を固定する(パートが分かれると、つなぐ日が無いまま終わる)
- 共通仕様の変更は横断役が一元管理。各パートは【修正案】を自分の設計書に書き、合意後に共通仕様へ(サーバーが既にこの運用)
- 実測の記録(方法・回数・条件。1 回だけは参考値)は、サーバーとハードで揃っている。Web とデモにも適用
- Drive には仕様書と図、コードは GitHub(ハード: `tkitora/re-ray`。サーバー・Web のリポジトリは決まったらここに書く)

## 6. 危険と対策

| 危険 | 対策 |
|---|---|
| 技適機器での自作ファーム利用が認められない可能性 | 段階 0 で問い合わせ。段階 1〜2 を Wi-Fi で先に固め、LoRa 無しでもデモが成立する形にする |
| 文字起こしの持ち主がいない | §2 で 1 人を置く。方式は段階 0 で決める |
| GUIDE01 の台数 | 1 台なら、グラスは 1 人だけ付け、リレーは T-Beam 3 台で見せる |
| T-Beam の到着が遅れる | 段階 1 の T-Beam 作業だけが遅れる。他は進む |
| ポジション表を端末が持っていない状態 | グラスは番号で出す(「区域 3 へ移動」)。名前は Wi-Fi 接続時に同期 |
