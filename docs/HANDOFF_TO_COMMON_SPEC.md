## B. ハード側の変更案(共通仕様の更新をお願いしたい)

1. **LoRa パケット形式(05_LoRa)** — ハードの案は 17 バイト前後 + 署名 4 バイト(HMAC-SHA256 の先頭)。Drive の 10 バイト案との差は次のとおり。
   - ttl は先頭バイトの下位 3bit(最大 7)。署名の計算からは外し、中継で書き換えても有効
   - 種別は REPORT / SOS / INSTRUCT / ACK / BEACON(実測用)の 5 つ
   - `dst` は持たない(上りは常にサーバー宛、下りは INSTRUCT の target で指定)
   - 署名がない 10 バイト案は、誤受信や単純ななりすましを防げない。署名は最小限の HMAC のみで、本格的な認証ではない
   - 詳細: `docs/MESSAGE_SPEC.md`
2. **定型信号コードを LoRa に載せる** — REPORT の `flags` の bit3〜7(5bit)に Drive の定型信号コード(0〜31、0=指定なし)を載せる。SOS フレームは code=1。これで 01 のコード 1〜4 がサーバーの signal の `code` まで届く。
3. **signal の追加項目 `x`** — 試験用に、区域・人数区分・GPS 有無・RSSI・SNR を `"x":{...}` に入れて出せる。サーバー側が無視してよいなら現状のままで可、不要なら出さない設定にできる(`withExtras=false`)。
4. **ack の扱い(02)** — LoRa の ACK は 3 種類(近傍に届いた / サーバー到達 / 指示受領)。MQTT の ack に出すのは「指示受領」だけ(`ack_src` は指示の送信元、`ack_seq` はその seq)。他の 2 つは LoRa の中だけで使う。

## C. 決まっていないこと(Drive 側の判断が必要)

1. **下りの text を LoRa でどう運ぶか(05_LoRa の「出口の端末までサーバーからの text を逆向きに流すか」)**
   - 現状の INSTRUCT は 18 バイトで、自由な文字は載らない(code と param のみ)
   - 案1: 定型の指示コード表(待機、移動、集合、撤収、物資搬送、流入停止、退避など)を共通仕様に作り、サーバーは `text` の代わりに(または一緒に)`code` を送る
   - 案2: 短い文字(数十バイト)を複数フレームに分割して送る(送信時間と電波法の制限が厳しくなるため、ハードとしては非推奨)
   - 案3: LoRa では text を運ばず、Wi-Fi が生きている端末にだけ届ける
   - ハードの推奨: 案1 → **10/20 に案1で決定**(B' 参照)
2. **送信時間の制限** — 920MHz 帯の連続送信時間と休止時間。ハード側で規格(ARIB STD-T108)を確認し、結果を `docs/COMPLIANCE.md` に書く。確認が済むまで保守的な暫定値(1 時間あたり 18 秒、1 回 1 秒)で動かし、**LoRa の送信は無効のまま**。status の間隔や中継の待ち時間は、この結果に合わせて決める
3. **status の送信間隔(30 秒案)** — 端末が LoRa でしか届かない状態では、30 秒ごとの status は送信時間の予算を食う。LoRa 経由では間引く案(例: 数分に 1 回)でよいか
4. **端末IDの書き込み方法** — ハードは `include/secrets.h` のビルド設定を想定。配布の仕方は 01 の「決めること」と同じ
